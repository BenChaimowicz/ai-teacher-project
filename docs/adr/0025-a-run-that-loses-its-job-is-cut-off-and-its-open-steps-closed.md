# A run that loses its job is cut off, and the next claim closes the steps it left open

On 2026-10-25 a Retry waited 3 minutes to be claimed, and the run that finally claimed it left two Pipeline Events `running` forever (SEN-93). Nothing was wrong with the claim. One worker was still finishing a Course the Learner had cancelled 3 minutes earlier, making 4 more paid calls, because Cancel took effect only at the next stage (ADR 0012). The other worker came back, claimed the Retry, and died within 20 seconds without handing it back, so the job waited for its lease to lapse. A step closes only when it returns or throws (ADR 0008), so the dead run's steps never did.

A Course run's model and research calls now stop as soon as the worker learns the run lost its job. `GenerationControl` carries a `signal`. The heartbeat aborts it, with a `LeaseLostError` as the reason, when a renewal finds the claim gone: the Learner cancelled, or another worker took over a lapsed lease. The run's OpenRouter transport and its research `fetch` are bound to that signal, so a call in flight throws the loss. The ports never retry it or hand it to the fallback model. The run then ends with `LeaseLostError` and records nothing. A worker is free within a third of the lease (20 s) of a Cancel, not when its stage ends. Blueprint runs are not cut off: the Learner can't cancel one, and their one write already checks the lease.

Every Pipeline Event a worker's run starts records the claim token it ran under (`pipeline_events.claim_token`), through the tracking context. Each claim then closes, in one statement, every `running` event whose claim no running job holds any more. Its run was killed, hung, shut down mid-step, or cancelled while its worker was down. Each one becomes `failed` with a "lease lost" error, finished at its last sign of life: its own start, its latest child step, or its latest Usage Record. A run that was alive after all overwrites this when it stops. Steps the API runs have no claim token and are never touched. Migration 0027 closes, the same way, the steps left running from before this change.

The claim is one `WITH … UPDATE … FROM` statement, not `UPDATE … WHERE id = (SELECT …)`, so it can return the row as it was. The worker logs, with each claim, how long the job waited and how long ago any lease it took over had lapsed, along with its owner, host and commit. The worker's pool is 10 connections, not 2 (decision 2026-10-30), so postgres.js does not pipeline its queries onto busy pooler connections. A claim or renewal still pending after 10 s is logged.

Rejected:
- **A dedicated `abandoned` status.** It would keep failure totals about steps that really failed, but every Console badge, label and filter would need it, for a case the error text explains.
- **Closing a run's steps in the shutdown handler only.** A process that is killed outright never runs it: on Windows, a `tsx watch` restart terminates the worker with no signal handler run. Only the next claim always sees the loss.
- **Polling for Cancel more often than the heartbeat.** Each check is a database round trip. 20 s is short next to a 3–7 minute stage.
- **A server-side `statement_timeout` for the worker.** Supabase's pooler ignores it at connection time (it stays at the role's 2 min), and it cannot catch a query the pooler lost, which never reaches the server.
